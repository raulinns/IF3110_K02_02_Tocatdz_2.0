## Boundaries and M1 compatibility

New public Go types live in `migration/types_m2.go`, ports in `ports_m2.go`.
Names deliberately coexist with `Migration`, `Draft`, `Repository`, `Status` and
`Application` from M1. Do not reuse M1 `Pending` as queue state: it means an
uncertain outcome. The integrator will backfill/translate it to M2 `uncertain`.

Domain structs are not JSON DTOs. SQL, predicates, trace carriers and recovery
references use `security.Secret`. Explicit API mapping reveals only authorized
fields; never add a generic reflection serializer or print domain values as logs.
No handler/worker/store implementation is introduced in this contract stage.

List ports return SQL-free summaries. Execution details expose the immutable
template separately; expanded statement records are paginated. Position stores
summary references and revalidation fetches only the targeted full execution.
Checkpoint iteration uses batch-number keyset cursors, including reverse order,
so large migrations do not require loading all batches into memory.

## Identity, ordering and immutable definition

IDs are canonical nonzero lowercase UUIDs. A zero `security.ID` inside Go means
absent; map to explicit JSON null where K1 permits it. Times are UTC. Page/limit
defaults are 1/50, limit <=200, offset <=1,000,000. Sort ties by ID as specified
in K1. Counts/revisions in HTTP stay within JavaScript's exact integer range;
PostgreSQL bigint cursor values use decimal **strings**, including negative keys.

Migration definition, CR, job, attempt and execution are different identities:

- Migration revision/checksum identifies the SQL and batch definition reviewed.
- CR revision is a separate CAS token incremented by decisions/transitions.
- A job is unique per CR. A duplicate execute returns the existing job.
- Attempt increases with claims; queued job starts at attempt 0. Retry does not
  allocate a new execution identity or a second logical history record.
- Receipt execution ID is allocated at enqueue and retained on retry/resume.
  Rollback, forward and compensation allocate new receipt execution IDs.
- Resume creates a new CR/job referencing the source job, but retains the source
  receipt execution ID/checkpoint namespace. A completed resume appends the one
  logical execution under that identity, referring to the completing CR/job.

Definitions contain full normal-mode SQL or K4 UPDATE assignment fragments.
Down SQL is required unless irreversible with a nonblank reason. An irreversible
definition has null down SQL; a reversible one has an empty reason. Batch config
is non-null exactly for mode=batch. Trimming is used only to detect blank inputs;
stored SQL bytes are not silently rewritten after review.

### Checksum version 1

Hash **SHA-256 over UTF-8 bytes of one compact JSON object**, no BOM/newline.
Use Go `encoding/json` with HTML escaping disabled; remove the encoder's final
newline. Property order is exactly the order below, with no extra properties:

```json
{"checksum_version":1,"title":"Example","up_sql":"SELECT 1;","down_sql":"SELECT 1;","irreversible":false,"irreversible_reason":"","mode":"normal","batch":null}
```

When batch is non-null its property order is `schema`, `table`, `key_column`,
`batch_size`, `scope_where`. Optional empty predicate is canonicalized to null.
All other values are exact validated bytes. Include title and reason so the
reviewed definition cannot change without checksum/revision change. Exclude IDs,
timestamps, state and revision. The SQL byte limits apply **per direction**.
Use the [checksum fixture](../../api/examples/checksum-v1.json) as a test vector.
The M1 `Checksum(SQL)` function is different and must remain untouched during
coexistence. Clients treat checksum as opaque; no browser hash implementation.

## State transitions

The definition owns `draft -> frozen` at successful submission. A CR starts in
`pending_review`; do not create an unrelated CR draft that can diverge from the
migration draft. PDF UI label "Pending (Queue)" maps to wire value `queued`.

| From CR | To CR | Condition |
|---|---|---|
| pending_review | approved | Every snapshotted group has one valid approve |
| pending_review | rejected | One valid reject |
| approved | queued | Atomic enqueue after rechecking definition/approval/position |
| queued | running | Worker has lease + target lock + successful revalidation/CAS |
| queued | failed | Revalidation fails without dispatch, or attempts exhausted |
| running | succeeded | Proven full commit, history and position persisted |
| running | failed | Proven no commit, no partial batches, no further retry |
| running | queued | Retryable proven failure, failed attempt recorded, backoff persisted |
| running | partial | Some original batches committed and work interrupted |
| running | partially_reverted | Some compensation batches committed, not all |
| running | uncertain | Commit outcome cannot yet be proved |
| uncertain | succeeded/failed/partial/partially_reverted | Receipt/checkpoint reconciliation proves actual outcome |

Rejected/succeeded/failed are final for that CR. Partial/partially_reverted keep a
database recovery barrier: recovery creates a **new** CR/job, never rewrites the
old CR back to queued. An uncertain job is reconciled before new recovery work.
Do not classify absence of a platform history record as absence of a target commit.

Job `running` includes waiting for target lock/revalidation. At that point CR can
still be queued; UI uses job for processing status. CR becomes running only at
`StartRunning`. A failed attempt may coexist with a queued job awaiting backoff.
`finished_at` is null while queued/running; terminal job statuses have a time.
`partial=true` means incomplete original work or compensation is committed;
an uncertain job with no known partial work may have partial=false.

No generic public `Transition(from,to)` is exposed: domain mutations use the
transaction boundary and worker mutations use lease-fenced lifecycle methods.

## Platform transactions and cross-worker guarantees

`WorkflowStore.WithWorkflow` scopes all reads/writes to one database and verifies
active requester, session and AuthVersion in the transaction. It locks a durable
per-database workflow guard row. Authorization/grant/leader changes affecting that
database must lock the same guard(s), in sorted database ID order, avoiding stale
approval decisions and deadlocks. A callback error rolls back every mutation.

Submission validates SQL first, then rechecks the same revision/checksum under
this transaction, freezes definition and creates CR/required-approval snapshot.
Reject empty required groups and missing/inactive leaders. One open CR per DB
is a team simplification. Existing partial/uncertain barriers are separate from
open review status: only a matching recovery lineage can pass the barrier.

`RecordDecision` checks expected CR revision, pending status, actor leadership,
snapshot identity and self-approval policy. A decision is immutable. Exact replay
of actor/group/decision/note returns existing state without another decision, even
with the original revision. A changed decision conflicts. Decide one group per
call; the request's group_id is mandatory.

`EnqueueApproved` checks revision for a **new** enqueue, all current approvals,
definition and expected position. Insert job and approved->queued in the same
transaction. Unique CR ID makes exact replay idempotent even with original CR
revision; always reauthorize the caller. Conflicting spec fields return conflict.
Ignore newly generated candidate IDs, timestamps and carrier on an otherwise
identical replay of the same CR; these are server outputs, not a new operation.
Return existing job's current status on replay; 202 does not guarantee queued.
No target SQL is executed from this path.

Worker claim uses persistent leases and `FOR UPDATE SKIP LOCKED`, excluding DBs
with running or recovery barriers except the authorized recovery lineage. A
monotonic fencing token prevents an expired owner finishing someone else's claim.
The cross-process target advisory lock protects the same actual target even when
two managed connections alias it; hold across batch commits. Revalidation uses
current active requester/grants **not the browser session** (logout/idle does not
invalidate already queued approved work). Account disabling or revoked write grant
does invalidate execution. Recheck CR/definition/approval/position under the platform
guard when `StartRunning` CASes state and freezes first-dispatch metadata.

Do not hold a platform transaction for an entire long target migration. Changes
to policy after StartRunning apply to future dispatches; they do not retroactively
undo committed work. Revalidate after reacquiring a lock on every retry/resume.

Target commit and platform completion are not distributed-atomic. Record target
receipt/checkpoint **in the same target transaction** as SQL, then atomically append
execution + update position/attempt/job/CR in platform DB. Reconcile after a crash.
`CompleteCommitted` is idempotent by execution identity and rejects mismatched
receipt data. Unknown outcome is uncertain and blocks following work.

Persist the immutable execution plan at StartRunning, including source direction,
original target execution and frozen scope. Revalidation of chained recovery reads
that SourcePlan and SourceJob rather than inferring direction from the latest
kind=resume alone. Keep protected SQL plan storage out of public job JSON.

## Rollback, forward, batch and history

Position is a consistent snapshot of active stack (oldest->newest), redo chain
(next->last), a monotonic version and blocking job. Increment version on position
or barrier changes. A rollback targets the latest active **UP execution ID** and
uses its original down. Forward targets the next original UP execution in redo
order and uses its original up, recording `forward_of_execution_id`.
After rollback C then B, forward B then C, one CR/job per step. New apply while
redo is nonempty conflicts; preserve linear history instead of silently branching.
SQL failure does not move the position. Irreversible cannot be rolled back.

Executed SQL/definition snapshots are immutable; new attempts cannot replace them.
Successful rollback sets `reverts_execution_id` to the exact active execution it
undoes (which can itself be a forward execution). Hide rollback pairs committed
rows by that ID across the full history **before** pagination, removing original
and successful rollback together. Never match by migration name or hide later
forward. [history-hide-rollback.json](../../api/examples/history-hide-rollback.json)
captures the PDF's E1–E5 example. SQL failure remains visible in jobs/attempts/logs.

For batch, set a fixed scope_max once, cursor initially null (not 0), then persist
exact affected scope, batch number, cursor and recovery data alongside the UPDATE
inside each target transaction. No entire dataset in memory. Counts mirror only
proven target commits and are reconstructed after lost platform updates. The key
is unique/non-null/immutable PostgreSQL integer, identifiers separately quoted,
and scope_where is parsed/allowlisted, not blindly interpolated. The runner owns
these K4 checks. Mutating the key or arbitrary multi-statement batch SQL is invalid.

Range boundaries alone may be insufficient for safe compensation (new rows,
mutable predicates or non-invertible updates). Do not re-evaluate today's predicate
as the affected set: persist exact keys/old values as needed or reject unsafe revert
with `unsafe_revert`. Compensation executes approved down in reverse batch order;
persist compensation checkpoints atomically too. Resume follows original receipt
identity; resuming partially_reverted means continue compensation, not run up.

History stores one complete logical committed operation; individual committed
batches of an incomplete operation stay in durable checkpoints/job metadata.
When resume completes, append the completed operation once. When partial work is
fully compensated, append a completed `revert_batches` DOWN execution with no
`reverts_execution_id` if there was never a complete original history execution;
clear its barrier without moving the prior active stack. This does not invent an
uncommitted UP history row. Retain all original job/checkpoint records. Recovery of
a partial rollback follows its source direction; the original full execution stays
active until the whole down operation completes. Unsafe reversal requires a new
repair migration through the blocked-lineage recovery policy, not a bypass.

In this first K4 contract, revert_batches cancels partially committed UP work or
continues a partially_reverted compensation. A partial DOWN rollback can be
resumed in its approved down direction; attempting to cancel it by silently
running up is rejected. Any broader compensation policy requires a reviewed
contract change. A repair is a new migration plus kind=apply CR whose source_job_id
explicitly identifies the latest partial/partially_reverted blocking lineage.
It requires fresh permission/validation/all approvals and a new receipt identity.
It cannot bypass uncertain outcomes, must match the DB/position/barrier snapshot,
and may replace only that barrier when its repair fully commits. Preserve original
partial jobs/checkpoints; do not fabricate their successful UP history. Repair SQL
is reviewed as a new definition, never substituted into the original migration.

## Errors and validation

Ports return `security.ErrInvalidInput`, `ErrNotFound`, `ErrConflict`,
`ErrUnauthenticated`, `ErrForbidden`, `ErrUnavailable` via errors.Is. Drivers never
leak their text. K1 distinguishes malformed transport (400), domain field/SQL
validation (422), result-too-large (422), CAS/workflow conflict (409), body-too-large
(413), unsupported media type (415), unavailable (503) and unexpected error (500).
The M1 HTTP text writer is not K1's JSON error writer.

Authorization occurs before exposing resource content. Every DB-scoped lookup
includes DatabaseID; cross-database IDs are not found after access checks. A
`JobLocator` resolves job DB internally for the unscoped /jobs/{id} route, then
requires job.view. Read-only users can read jobs, attempts and history.
